The `mqtt` source now supports end-to-end acknowledgements. When `acknowledgements` is enabled, the QoS 1 `PUBACK` for an incoming publish is deferred until the resulting events have been delivered to all connected sinks. Because the source already uses `clean_session = false` and subscribes at QoS `AtLeastOnce`, an unacknowledged message is redelivered by the broker after a crash or reconnect, providing at-least-once delivery when the broker resumes the persistent session. If delivery fails with an error, the source withholds the acknowledgement and reconnects so the broker redelivers the message; an event that a sink rejects outright is acknowledged and dropped, with an error logged, because redelivering it cannot succeed.

Acknowledgements require a stable `client_id`, so the session (and its unacknowledged messages) can be resumed after a restart, and a non-zero `keep_alive`. Enabling `acknowledgements` on the source without them is a configuration error. If acknowledgements are enabled only by the global option or by a connected sink, a source without them logs a warning and keeps running without acknowledgements, as it did before. Publishes delivered by the broker with QoS 0 cannot be acknowledged end-to-end and are forwarded with a warning instead of being registered for deferred acknowledgement. The source also warns if the broker starts a new session while acknowledgements are enabled, since unacknowledged messages from the previous session for that client ID will not be redelivered.
