# Antithesis Tests

This directory contains Vector's Antithesis workloads and scenarios. The current
focus is testing event conservation, integrity, and post-fault liveness across
Vector topologies, especially topologies using `disk_v2` buffers.

## Layout

- `Dockerfile` builds the instrumented Vector binary and the shared workload
  image used by every scenario.
- `harness/` contains the oracle, producer, eventual-phase judge, and their
  shared protocol and HTTP clients.
- `scripts/launch.sh` builds, renders, and submits any named scenario.
- `scenarios/<name>/` owns only that scenario's Compose topology, Vector
  configuration, launch settings, and rationale.
- `.launch/<name>/` is generated by the launcher and contains the fully rendered
  Compose configuration submitted to Antithesis.

## Shared Test Model

The workload is independent of a particular topology:

1. A producer claims a unique id from the oracle and submits a deterministic
   payload to the scenario's Vector HTTP source.
2. If Vector returns a successful end-to-end acknowledgement, the producer tells
   the oracle that delivery of that id is now an obligation.
3. The final sink delivers records to the oracle. The oracle validates both the
   id and the full deterministic payload.
4. In the fault-free `eventually_` phase, the judge waits for recovery and drain,
   checks all obligations, and sends a fresh event to test liveness.

Every scenario exercises the same properties:

- Every end-to-end-acknowledged event is eventually delivered.
- Every delivered id was issued by the oracle.
- Every delivered payload matches the payload generated for its id.
- The topology can deliver a fresh event after faults stop.
- Sufficient acknowledged traffic and duplicate replay are observed across the
  Antithesis exploration history.

The oracle owns the in-memory source of truth. It must not be terminated or hung;
network faults against its links are intentional and heal before the eventual
phase evaluates conservation.

## Running a Scenario

Prerequisites:

- [snouty](https://github.com/antithesishq/snouty)
- Docker with Compose
- Antithesis tenant credentials and repository environment variables described
  in [`AGENTS.md`](AGENTS.md)

From this directory:

```bash
docker compose -f scenarios/vector_e2e/docker-compose.yaml config
docker compose -f scenarios/vector_e2e/docker-compose.yaml build
./scripts/launch.sh vector_e2e
```

The launcher always builds from the current checkout, renders environment and
image-tag substitutions into `.launch/<scenario>/docker-compose.yaml`, and gives
that self-contained configuration to snouty. Use `DRY_RUN=1` to print the build,
render, and launch commands without executing them.

## Adding a Scenario

Create `scenarios/<name>/` containing:

- `docker-compose.yaml`, with Vector builds targeting the shared `Dockerfile`
  and passing `SCENARIO: <name>`;
- one or more Vector YAML configurations;
- `launch.env`, defining the test name, description, and faulted SUT nodes;
- `README.md`, describing only the topology-specific behavior and rationale.

Point the oracle's environment variables at the scenario's ingress and metrics
endpoints. The shared workload discovers the topology entirely through those
variables; a scenario-specific Rust binary or Dockerfile should not be needed.
